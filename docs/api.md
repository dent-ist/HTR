# HTR API (M2, repair tools M3, training M4, active learning M5, abbreviations and bundle M6, hardening M7)

Base URL `http://127.0.0.1:8000` (loopback only). Interactive docs generated by FastAPI: `/docs` (Swagger UI) and
`/openapi.json`. This page is the human summary. All bodies are JSON unless noted.

Status codes used: 200, 201 (created), 202 (job enqueued), 204, 400/421 (wrong `Host` header), 404 (not found),
409 (conflict with current state), 413 (upload too large), 415 (not a single-page PNG/JPEG/TIFF), 422 (invalid
input), 500 (unexpected), 503 (database busy, project being imported), 507 (disk full).

## Errors (one format everywhere)

Every error response, from any endpoint, has the same four keys:

```json
{"detail": "The project database is busy.", "code": "db_locked", "message": "The project database is busy.",
 "hint": "Another task is writing to it. Wait a few seconds and try again; ..."}
```

* `code` - a stable machine-readable id (for example `not_found`, `conflict`, `invalid_input`, `validation_error`,
  `file_missing`, `image_unreadable`, `image_too_many_pixels`, `multipage_image`, `upload_too_large`, `db_locked`,
  `disk_full`, `cuda_oom`, `no_model`, `no_ground_truth`, `job_active`, `llm_disabled`, `host_not_allowed`,
  `internal_error`). Safe to switch on.
* `message` - the same text as `detail`, in plain words. For 422 validation errors `detail` stays the list of
  `{loc, msg, type}` and `message` is a readable summary of it.
* `hint` - what the person can do about it, or `null` when there is nothing to add.
* Unexpected exceptions become a 500 with code `internal_error`: never a stack trace and never any of your text.
  Technical details (exception class and code location only) go to `data/logs/htr.log`.

Failed **jobs** carry the same information: `error` (message), `error_code` and `error_hint`.

## Host check (DNS-rebinding protection)

The server listens on 127.0.0.1 only and answers only requests whose `Host` header is `127.0.0.1`, `localhost` or
`[::1]` (optionally with a port). Anything else is refused before it reaches any endpoint: 421 `host_not_allowed`
(400 if the header is missing, malformed or repeated). CORS stays an exact allowlist of the two Vite origins.

Coordinates: every point is `[x, y]` in **working-copy pixels** (the image served by `/pages/{id}/working`), integers
(floats are rounded), and must lie inside the page. A polygon has at least 3 points, a baseline at least 2.

## Lines

| Method | Path | Notes |
|---|---|---|
| PATCH | `/lines/{id}` | partial update, any of `text, polygon, baseline, ignored, is_ground_truth, index`. See rules below. |
| DELETE | `/lines/{id}` | 204; later lines are renumbered |
| POST | `/pages/{id}/lines` | `{baseline, polygon, text?, ignored?, index?}` -> 201 line. Page must be segmented (409 otherwise). Default index = append. |
| GET | `/lines/{id}/crop.png` | working copy cropped to the polygon's bounding box |

Line object: `id, page_id, index` (0-based reading order), `baseline, polygon, text, text_source` (`manual`,
`predicted` or null), `confidence` (predictions only), `predicted_by_model_id` and `predicted_text` (see "Active
learning"), `is_ground_truth, ignored, crop_url`.

PATCH rules: setting `text` sets `text_source = "manual"` and clears `confidence` (empty text clears the source);
text is stored exactly as sent (diplomatic), max 2000 characters, no control characters; `is_ground_truth: true`
requires non-empty text; `index` moves the line to that position and shifts the others in one transaction (this is the
reorder operation); `null` values and unknown fields are rejected.

Every line change (and every segmentation) rewrites the page's PAGE-XML in the same operation as the DB commit; if the
rewrite fails the change is rolled back. See "PAGE-XML sync" in the README.

### Segmentation repair (M3)

All of these rewrite the PAGE-XML in the same transaction, keep `index` contiguous (0..n-1) and validate geometry
against the page. The ones that change several lines return `page`: the page object with its `lines`.

| Method | Path | Notes |
|---|---|---|
| POST | `/lines/merge` | `{line_ids: [a, b, ...]}` (2+, same page, any set). Creates one new line at the first input's reading-order position and deletes the inputs. Baseline: all baseline points left to right. Polygon: union of the polygons (convex hull if they are disjoint), clipped to the page. Text: non-empty texts joined by a space in reading order, `manual` source. `is_ground_truth` is reset to false, `ignored` is false. 422 on fewer than 2 / repeated ids / different pages / joined text over 2000 chars; 404 unknown id. -> `{line, removed_ids, page}` |
| POST | `/lines/{id}/split` | `{x, y}` (a point on the page; the cut is the vertical at `x`). The left half keeps the id, the right half is a new line right after it, both inherit `ignored`. Both texts are cleared and ground truth reset; the previous text is returned as `old_text`. Neither half keeps the
prediction (`predicted_by_model_id` and `predicted_text` are cleared on both: they are new lines nobody predicted) and
no review event is written; undoing the split gives the prediction back. 422 if `x` is not strictly inside the baseline or a half would be degenerate. -> `{lines: [left, right], old_text, page}` |
| POST | `/pages/{id}/lines` | `polygon` is now optional: with only a `baseline` (2+ points) the server builds the polygon by offsetting the baseline up and down by the page's median ascent/descent over the existing lines (fallback: 0.7 / 0.3 of the page's `line_height_px`), clamped to the page. The baseline is stored left to right. |
| PATCH | `/lines/{id}` | new field `regenerate_polygon: true`: re-derives the polygon from the new `baseline` in the same request (or from the current baseline if none is given). Not allowed together with `polygon`. This is "redraw baseline". |
| POST | `/pages/{id}/ignore-region` | `{x, y, w, h}` or `{polygon: [...]}`. Marks every not-yet-ignored line with at least 50% of its polygon area inside the region as ignored. For every
*predicted* line it ignores it writes an `ignored` review event in the same transaction, exactly as ignoring the line
through PATCH does. -> `{affected: [line ids], page}` |
| POST | `/pages/{id}/reorder` | `{line_ids: [...]}` the complete new reading order (every line of the page exactly once, else 422). -> page with `lines` |
| POST | `/pages/{id}/restore` | `{lines: [...], force?: false}` replaces the page's lines with a snapshot (this is the undo primitive; each snapshot line has the fields of a line object: `id` (kept when free, so undo restores ids), `baseline, polygon, text, text_source, confidence, predicted_by_model_id,
predicted_text, is_ground_truth, ignored`). The prediction state is given back **exactly** as the snapshot has it, also
on lines that are re-created because the operation deleted them (a `predicted_by_model_id` that names a model that no
longer exists is dropped); an `ignored` review event that retired the same prediction (an ignore-region being undone)
is withdrawn, so one prediction still yields at most one event. Merge makes a new, unpredicted line (inputs deleted;
text joined, source `manual`), split clears the prediction as described above, so undo is what brings predictions back. Refused with **409** if the page currently holds text whose words are not all present in the snapshot's texts (typed work would be lost) unless `force` is true. -> page with `lines` |

## Jobs

| Method | Path | Notes |
|---|---|---|
| GET | `/jobs/{id}` | `{id, type, status, payload, progress (0-1), error, result, created_at, started_at, finished_at}` |
| GET | `/jobs` | newest first. Filters `?status=`, `?type=`, `?limit=` (default 100, max 500) |
| POST | `/jobs/{id}/cancel` | a **queued** job is cancelled at once. A **running `train` or `predict`** job is asked to stop: the response is the job with `cancel_requested: true` (status still `running`); the handler stops at its next checkpoint (a training batch, a prediction page) and the job ends `cancelled`. 409 for a running `segment` job (cannot be interrupted) and for finished jobs. |

Statuses: `queued`, `running`, `succeeded`, `failed`, `cancelled`. One job runs at a time, in order. Job types:
`segment`, `train`, `predict` (M4, below) and `suggest` (optional, local LLM; below). A finished job's `result`
may hold `notices`: visible, non-fatal remarks, for example that no GPU was found and the job ran on the CPU. A job left `running` by a crash is marked `failed` ("interrupted") on the
next start. While a job runs, `result` holds its live status (for `train`: phase, epoch, loss, validation accuracy,
per-epoch history; for `predict`: counts so far); when it finishes `result` is the final summary. A job object also
has `cancel_requested`.

## Training, prediction and models (M4)

Engine: Kraken 7.1.1 recognition models (`engine: "kraken"` on every model row; the code is behind a
`Recognizer`/`Trainer` interface so another engine could be added). Training and prediction are user-triggered at any
time; nothing is ever refused for having "too few" lines, only warned about.

| Method | Path | Notes |
|---|---|---|
| POST | `/jobs/train` | body (all optional): `{epochs (1-500, default 15), batch_size (1-256, default 4; lower it on GPU out-of-memory), learning_rate (default 0.0001), base_model_id (default: the active model), device ("auto"\|"cpu"\|"cuda:0"), patience (early stopping, default 5), augment (default true)}`. -> 202 job plus `warnings`: a list of strings, e.g. "Only 24 ground-truth lines; about 100 are recommended for the first round...", "Only 6 new ground-truth lines since the last training round; about 50 are recommended...". 422 if there are no usable ground-truth lines or no start model exists (run `make base-model`); 404 unknown `base_model_id`; 409 if the model file is missing or a train job is already queued/running. |
| POST | `/jobs/predict` | body (all optional): `{model_id (default: active), page_ids (limit to these pages), batch_size, device}`. -> 202 job plus `warnings` (a note when the pretrained base model is used). 404 unknown model/page, 422 no model available, 409 a predict job is already queued/running. |
| GET | `/models` | the registry, newest first (see fields below) |
| GET | `/models/{id}` | one model, 404 if unknown |
| POST | `/models/{id}/activate` | makes it the model `predict` and the next fine-tune use by default (exactly one is active) |
| GET | `/training/summary` | counts and warnings the Training page shows, see below |

**Usable ground truth** = `is_ground_truth` and not `ignored` and non-blank text, on a segmented page.

**Train job.** Exports the usable lines to `data/training/run-<job id>/` (PAGE-XML per page and part `train/` `val/`
`eval/`, masked line crops with `.gt.txt` under `lines/`, `manifest.json` with the split), scores the start model on
the held-out lines ("before"), fine-tunes (AdamW, augmentation, early stopping on a validation subset of the training
lines, best epoch kept), scores the best epoch on the same held-out lines ("after"), writes
`data/models/<model id>.mlmodel` and registers the model. The new model is activated unless it is worse than its start
model on the held-out lines (then a warning in `result.warnings`). `result` (final): `{model_id, activated, epochs_run,
best_epoch, stopped_early, best_val_accuracy, cer, wer, base_cer, before, after, train_lines, held_out_lines,
validation_lines, seconds, training_seconds, device, peak_vram_mb, history: [{epoch, train_loss, val_accuracy,
seconds}], run_dir, warnings}`. `train_loss` is Kraken's CTC loss summed over the lines of a batch, so only its trend
means anything. A CUDA out-of-memory fails the job with a message suggesting a smaller batch size; the server is
unaffected.

**Held-out split.** A line is held out when `sha256("htr-split-v1:<line id>") mod 10000 < 1200` (about 12%). The first
run with at least 8 usable lines stores every line's side in `line_splits`; a line never changes side afterwards, so
CER is comparable across rounds. If that leaves no held-out line, the unassigned line with the lowest hash is held
out, so there is at least one whenever there are 8 or more usable lines. With fewer than 8, nothing is held out and
the run reports no CER. Held-out lines are never trained on or used to choose the epoch (a separate ~10% validation
subset of the training lines does that; with fewer than 10 training lines validation reuses them).

**Predict job.** Covers every line that is not ground truth, not ignored and has no manual text (earlier predictions
are replaced). It writes `text`, `text_source = "predicted"` and `confidence` page by page through the same
transactional PAGE-XML sync as every other edit. Ground truth and manual text are never overwritten, not even if the
user edits a line while the job runs. `result`: `{model_id, model, lines, predicted, unreadable, changed_meanwhile,
empty, pages, mean_confidence, seconds, device, cuda_fallback}`. If the GPU runs out of memory the batch is halved
and finally the CPU is used for that run.

**Confidence** is the geometric mean of the per-character confidences of the line (each character's confidence is the
highest softmax probability the network gave it), in [0, 1]; 0 for an empty prediction. Use it to rank lines for
review (lowest first), not as a calibrated probability.

**CER / WER.** CER = character edit distance / reference characters, compared exactly (no case folding, no
normalization, whitespace counts). WER = word edit distance / reference words after collapsing whitespace (case and
punctuation still count). Both are micro-averaged over the held-out lines (total edits / total reference length) and
can exceed 1.

Model object: `{id, name, kind ("base" pretrained \| "finetuned"), engine, path (relative to the data dir), base_model
(name of the start model), parent_model_id, trained_at, train_lines, eval_lines, cer, wer, base_cer, base_wer
(the start model on the same held-out lines), hyperparameters, split_info, metrics (per-epoch history, before/after
details), job_id, license, is_active}`.

`GET /training/summary`: `{ground_truth_lines, held_out_lines, unassigned_lines, projected_held_out_lines,
train_pool_lines, new_since_last_round, last_round: {model_id, trained_at, train_lines} \| null, recommended_first_round
(100), recommended_per_retrain (50), recommended (the one that applies now), predictable_lines, active_model, warnings}`.

## Active learning (M5)

**Where a prediction came from.** The predict job stores, per line, `predicted_by_model_id` (also in the line object;
null once the line has been reviewed or was never predicted) and a snapshot of the predicted text. These are what
correction effort is measured against.

**Review events.** When a predicted line is saved as ground truth through `PATCH /lines/{id}` (`is_ground_truth: true`
with or without new `text`), or is ignored, a row is written to `review_events` in the *same transaction* as the line
change (and rolled back with it): `accepted` (final text equals the prediction), `corrected` (it differs;
`edit_distance` = Levenshtein distance in characters) or `ignored`. One prediction yields at most one event. Lines that
were never predicted, and edits to ground truth afterwards, record nothing. PAGE-XML is unchanged: text, confidence
and flags are written as before.

| Method | Path | Notes |
|---|---|---|
| GET | `/review/next` | `?limit=1&exclude=1,2,3`. The lowest-confidence lines among predicted, not ground truth, not ignored lines (ties by line id), skipping the ids in `exclude` (skipping is client-side). `{items: [{line, page_id, crop_url, predicted_text, confidence, model_id}], remaining}`; `remaining` counts the queue after `exclude`. 422 if `exclude` is not a list of integers. |
| GET | `/review/queue` | `?lowest=N`: `{total, buckets: [{min, max, count}] (10 buckets of 0.1; 1.0 is in the last), mean_confidence, lowest: [...]}` |
| GET | `/review/stats` | Correction effort per model (= per round), oldest first: `{rounds: [{round, model_id, model_name, kind, trained_at, cer, wer (the model's held-out scores), reviewed, accepted, corrected, ignored, accepted_rate (accepted / (accepted + corrected)), mean_edits_per_line, mean_edits_per_char (edits / predicted characters)}], total_reviewed, accepted_rate}` |
| POST | `/jobs/round` | Same body, validation and `warnings` as `/jobs/train`; 202 with the train job (`payload.then_predict = true`, response `round: true`). When the train job succeeds **and** the new model is activated, it enqueues a predict job (`payload {model_id, round_job_id}`) over every line that is not ground truth; its id is the train job's `result.next_job_id`. If training fails or is cancelled, or the new model is worse than its start model (not activated), no predict job is created and the train job's status, `error` and `result.warnings` say why. The predict job is an ordinary job and can be cancelled separately. 409 while a train job is queued or running. |

`GET /training/summary` also returns `retrain_suggested` and `retrain_reason`: true when there are at least 50 new
ground-truth lines since the last round, or (before any trained model exists) at least 100 in total. It is advice
shown as a notice; training is never blocked. `new_since_last_round` was already there.

## Optional local-LLM abbreviation suggestions (M7)

Off by default (`HTR_LLM_ENABLED`). The app then never opens a connection to a language model. When enabled it talks
only to a server on this computer (`HTR_LLM_URL`, default `http://127.0.0.1:11434` = Ollama; `HTR_LLM_API=openai` for
an OpenAI-compatible server such as llama.cpp's `llama-server`). A URL whose host is not a loopback address is refused
when the settings are read, and again before every request; redirects are not followed.

What is sent for one abbreviation: the token, the line that contains it and (optionally) up to `llm_context_lines`
neighbouring lines on each side (default 1, at most 2), each cut to 300 characters. Only text the user wrote or
confirmed is used (never raw predictions); no page, document or file names, ids or other text. The answer is stored as
`suggestions` rows. A suggestion is never applied to a transcription: accepting one only creates a dictionary entry.

| Method | Path | Notes |
|---|---|---|
| GET | `/abbreviations/suggestions` | `?status=pending\|accepted\|rejected\|all` (default `pending`) -> `{enabled, backend: {api, url, model} \| null, items: [{id, written, expansion, rationale, line_id, context, model, status, abbreviation_id, created_at, resolved_at}]}`. Works while the feature is off, so earlier suggestions stay reviewable. |
| POST | `/abbreviations/suggestions/generate` | body (all optional) `{tokens: [..], max_tokens (1-100, default 25), context_lines (0-2)}` -> 202 job of type `suggest`. Without `tokens` the app picks abbreviation-like tokens (containing `/` or an inner `.`, short ALL-CAPS, or very short lowercase words that are not everyday words) from verified text that are not unambiguous dictionary entries and have no suggestion yet. One job at a time (409 `job_active`); cancellable with `POST /jobs/{id}/cancel` (what was answered before is kept). 409 `llm_disabled` while the feature is off. Result: `{tokens, asked, suggestions_added, model}`. Failures carry codes such as `llm_unreachable`, `llm_timeout`, `llm_model_missing`, `llm_server_error`. |
| POST | `/abbreviations/suggestions/{id}/accept` | optional body `{written, expansion, notes, case_sensitive}` to edit before accepting. Creates the dictionary entry (or links the identical existing one) and marks the suggestion `accepted`. -> `{suggestion, abbreviation}`. 409 if it was already decided; 422 if the edited entry is invalid (the suggestion stays pending). |
| POST | `/abbreviations/suggestions/{id}/reject` | marks it `rejected`. The (written, expansion) pair is remembered: it is never suggested again. |
